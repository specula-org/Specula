## Requirement-evidence annotations in old/spec

The old model carries a `REQ-EVIDENCE` comment block above each checked property. The blocks were written from the old revision only, by reviewers who did not see this update. Each block has these fields:

- `intent`: what the property means, in plain English.
- `status`:
  - `requirement`: non-implementation evidence (protocol, doc, comment stating a rule, proto, test, history) supports the intent.
  - `impl-abstraction`: the property only describes how the old code worked.
  - `unknown`: it looks like a correctness requirement, but only implementation evidence was found.
  - `model-internal`: a check about the model itself.
  - `mixed`: the clauses have different statuses, listed in `clause` lines.
- `evidence`: cited sources. Each non-implementation line ends with `->` and the part of the intent that the line supports.
- `watch`: source locations whose change should trigger a review of this property.
- `note`, `clause`, `review`, `relabel`: remarks, per-clause statuses, and the reviewers' corrections.

Use them as follows. Where these rules and the rules above disagree, these rules take precedence for annotated properties.

1. Read a property's block before you decide anything about that property.
2. If update.patch touches any `watch` location of a property, re-examine that property explicitly against the new source, and say so in its entry, even if you then keep it.
3. `requirement`, or a `requirement` clause:
   - The new code is expected to obey it. Do not weaken or narrow it to match the new implementation.
   - If the new source no longer satisfies it, keep it and record the mismatch as a suspected implementation defect.
   - The exception is new non-implementation evidence in new/source or update.patch (a comment stating the rule, a doc, a proto comment, a test assertion) showing that the requirement itself changed. If you have such evidence, cite it.
4. `impl-abstraction`, or an `impl-abstraction` clause:
   - It describes old behavior. If the update changes that behavior, revise it to describe the new behavior, and bound the revision by what the new source and its non-implementation evidence support.
   - Do not keep it unchanged without checking it against the new source.
5. `unknown`, or an `unknown` clause:
   - Do not weaken it toward the new implementation.
   - If the update conflicts with it, mark it unresolved and state what evidence would settle it.
6. `mixed`: apply rules 3–5 clause by clause.
7. The annotations can be wrong. If the evidence you find contradicts a block, say so and cite the evidence.

In every decision entry for an annotated property, add the field `ledger_status` (the block status, or the clause statuses you relied on) and `watch_touched` (true/false). For every revised or added property, include an updated `REQ-EVIDENCE` block in the same format.
